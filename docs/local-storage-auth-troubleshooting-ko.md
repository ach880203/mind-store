# DB 없이 로그인, 주문, 예약을 기억하는 방법

## 1. 이 프로젝트가 DB 없이도 기억할 수 있는 이유

이 프로젝트는 서버 DB 대신 브라우저의 `localStorage`를 작은 임시 데이터베이스처럼 사용합니다.  
즉, 사용자가 회원가입을 하거나 로그인하고, 상품을 주문하거나 상담을 예약하면 그 데이터를 브라우저 안에 문자열(JSON) 형태로 저장해 두고, 다음 화면에서 다시 읽어 와서 보여주는 방식입니다.

핵심은 "한 화면만 저장하는 것이 아니라, 사용자 페이지와 관리자 페이지가 같은 저장소 키를 같이 본다"는 점입니다.

예를 들면 아래처럼 역할을 나눌 수 있습니다.

- `mind_current_user`
  - 현재 로그인한 사용자 정보
- `admin_users_v1`
  - 회원 목록
- `admin_orders_v1`
  - 주문 목록
- `mind_reservations_v1`
  - 상담 예약 목록
- `admin_products_v1`
  - 관리자에서 수정한 상품 목록

이렇게 하면 DB가 없어도 같은 브라우저 안에서는 상태를 계속 기억할 수 있습니다.

## 2. 실제 동작 흐름

### 2-1. 로그인은 어떻게 기억하나

1. 사용자가 로그인 화면에서 아이디와 비밀번호를 입력합니다.
2. 코드가 `admin_users_v1`에 저장된 회원 목록을 읽습니다.
3. 일치하는 회원을 찾으면 그 사용자 객체를 `mind_current_user`에 저장합니다.
4. 헤더, 마이페이지, 예약/주문 화면은 `mind_current_user`를 읽어서 "지금 누가 로그인했는지"를 판단합니다.

즉, 로그인 상태는 세션 서버가 아니라 브라우저 저장소에 들어 있는 현재 사용자 정보로 판단합니다.

### 2-2. 상품 주문은 어떻게 기억하나

1. 로그인한 사용자가 상품 페이지에서 `바로 주문` 버튼을 누릅니다.
2. 코드가 현재 로그인 사용자(`mind_current_user`)를 읽습니다.
3. 상품명, 가격, 수량, 사용자 아이디를 묶어서 새 주문 객체를 만듭니다.
4. 그 주문 객체를 `admin_orders_v1`에 추가 저장합니다.
5. 마이페이지 주문 내역과 관리자 주문 관리는 같은 `admin_orders_v1`를 읽기 때문에 즉시 같은 데이터를 보게 됩니다.

즉, "사용자 주문 화면"과 "관리자 주문 화면"이 서로 다른 데이터를 쓰는 것이 아니라, 같은 주문 배열을 함께 읽고 수정합니다.

### 2-3. 상담 예약은 어떻게 기억하나

1. 로그인한 사용자가 상담 예약 화면에서 날짜와 시간을 선택합니다.
2. 코드가 현재 로그인한 사용자 정보를 읽습니다.
3. `userId`, `userName`, `counselingId`, `date`, `time`, `status`를 포함한 예약 객체를 만듭니다.
4. 그 객체를 `mind_reservations_v1`에 저장합니다.
5. 마이페이지 예약 내역과 관리자 예약 관리는 같은 `mind_reservations_v1`를 읽어서 보여 줍니다.

관리자가 예약 상태를 `대기`, `확정`, `완료`, `취소`로 바꾸면 같은 저장소 배열이 수정되기 때문에 사용자 마이페이지에서도 바로 같은 상태가 보입니다.

### 2-4. 왜 마이페이지에서 "내 것만" 보여줄 수 있나

주문이나 예약 전체 목록을 그대로 보여 주는 것이 아니라, 현재 로그인한 사용자의 `user_id`, `name`, `nick`를 기준으로 필터링하기 때문입니다.

예를 들면 아래 순서입니다.

1. `mind_current_user`에서 현재 사용자 정보를 읽습니다.
2. 그 사용자와 연결되는 식별값(`user_id`, `name`, `nick`)을 모읍니다.
3. 주문 배열과 예약 배열을 돌면서 이 식별값과 일치하는 데이터만 남깁니다.
4. 남은 데이터만 마이페이지에 보여 줍니다.

그래서 DB가 없어도 "누가 예약했고 누가 주문했는지"를 계정 기준으로 다시 보여 줄 수 있습니다.

## 3. 이 방식의 장점과 한계

### 장점

- 서버 없이도 포트폴리오에서 로그인/회원가입/마이페이지 흐름을 만들 수 있습니다.
- 관리자 페이지와 사용자 페이지를 같은 데이터로 쉽게 연결할 수 있습니다.
- 배포가 단순하고, 프론트엔드만으로도 전체 서비스 흐름을 보여 줄 수 있습니다.

### 한계

- 브라우저를 바꾸면 데이터가 공유되지 않습니다.
- 사용자가 직접 `localStorage`를 지우면 데이터가 사라집니다.
- 보안이 필요한 실제 로그인 시스템으로는 사용할 수 없습니다.
- 여러 사용자가 동시에 접속하는 실제 서비스 구조는 아닙니다.

즉, 포트폴리오나 프로토타입에는 적합하지만, 실서비스에서는 서버 DB와 인증 API가 필요합니다.

# 초보자가 어려움을 겪기 쉬운 부분과 트러블슈팅

## 트러블 1. 회원가입은 됐는데 로그인이나 관리자 페이지와 연결되지 않는 문제

### 문제 상황

- 회원가입 화면에서는 새 회원을 만들었다고 생각했는데
- 로그인 화면에서는 새 계정으로 로그인이 안 되거나
- 관리자 회원 관리 화면에서는 새 사용자가 보이지 않는 문제가 생길 수 있습니다.

### 원인

각 화면이 서로 다른 데이터를 보고 있었기 때문입니다.

- 로그인은 `usersdb.js` 더미 배열만 읽고
- 관리자 회원 관리는 `admin_users_v1`를 읽고
- 회원가입은 또 다른 위치에 저장하면

화면마다 기준 데이터가 달라집니다.

즉, "회원 데이터의 단일 출처"가 없어서 생기는 문제입니다.

### 해결 방법

`userStore` 유틸을 만들어서 회원 데이터를 무조건 한 군데로 읽고 저장하도록 통일했습니다.

- `initUsers()`
- `loadUsers()`
- `saveUsers()`
- `findUserByCredentials()`
- `createUser()`
- `updateUser()`

이제 로그인, 회원가입, 관리자 회원 관리, 마이페이지 수정이 모두 같은 `admin_users_v1`를 사용합니다.

### 결과

- 회원가입한 계정으로 바로 로그인할 수 있습니다.
- 관리자 회원 관리에서도 같은 회원이 보입니다.
- 마이페이지에서 회원정보를 수정하면 관리자 화면에도 반영됩니다.

### 포트폴리오용 한 줄 정리

"회원 관련 화면이 각각 다른 더미 데이터를 보고 있던 구조를 공통 저장 유틸로 통합해, 회원가입-로그인-관리자 회원 관리가 하나의 데이터 흐름으로 연결되도록 개선했습니다."

## 트러블 2. 로그인은 되었는데 마이페이지에서 내 주문/예약이 안 보이는 문제

### 문제 상황

- 로그인은 성공했는데
- 마이페이지 예약 내역이나 주문 내역이 비어 보이는 현상이 생길 수 있습니다.

### 원인

현재 로그인 사용자 정보를 너무 적게 저장하면 필터링 기준이 부족해집니다.

예를 들어 로그인 성공 후 아래처럼 일부 값만 저장하면:

- `user_id`
- `nick`
- `admin`

주문 데이터는 `name`으로 저장되어 있고, 예약 데이터는 `userName`으로 저장되어 있으면 서로 정확히 연결되지 않을 수 있습니다.

즉, "로그인 정보"와 "주문/예약 데이터의 사용자 식별값"이 맞지 않는 문제가 발생합니다.

### 해결 방법

로그인 성공 시 사용자 전체 객체를 `mind_current_user`에 저장하도록 바꿨습니다.

그리고 마이페이지에서는 아래 값을 함께 사용해 필터링합니다.

- `user_id`
- `name`
- `nick`

즉, 한 가지 값만 믿지 않고 여러 식별값을 함께 비교해 현재 사용자와 연결된 주문/예약만 모아 보여 주도록 만들었습니다.

### 결과

- 기존 더미 데이터와 새로 생성한 데이터가 더 안정적으로 연결됩니다.
- 마이페이지에서 "내 기록만 보기"가 훨씬 정확해집니다.

### 포트폴리오용 한 줄 정리

"로그인 상태에는 사용자 전체 객체를 저장하고, 마이페이지에서는 `user_id`, `name`, `nick`를 함께 비교해 사용자별 주문/예약 내역이 안정적으로 매칭되도록 개선했습니다."

## 트러블 3. 예약 완료 화면은 뜨는데 실제 예약 내역은 남지 않는 문제

### 문제 상황

- 예약 화면에서 날짜와 시간을 고르고 `예약확정`을 누르면
- 완료 메시지는 보이는데
- 관리자 예약 관리나 예약 확인 화면에는 새 예약이 없을 수 있습니다.

### 원인

화면 상태만 바꾸고 실제 저장을 하지 않았기 때문입니다.

즉, `setDone(true)` 같은 UI 상태는 바뀌었지만, 예약 배열에 새 데이터를 추가하는 코드가 없으면 새로고침 후 사라집니다.

### 해결 방법

예약 확정 버튼에서 `addReservation()`을 호출하도록 바꿨습니다.

여기서 아래 정보를 함께 저장합니다.

- 현재 로그인 사용자 아이디
- 사용자 닉네임
- 상담 상품 ID
- 예약 날짜
- 예약 시간
- 기본 상태값(`대기`)

즉, "예약 완료 화면 표시"와 "실제 저장"을 분리하지 않고 한 흐름으로 연결했습니다.

### 결과

- 사용자가 예약한 내용이 마이페이지 예약 내역에 바로 보입니다.
- 관리자 예약 관리 화면에서도 같은 예약이 확인됩니다.
- 상태를 바꾸면 사용자/관리자 화면이 함께 동기화됩니다.

### 포트폴리오용 한 줄 정리

"예약 완료 UI만 바뀌던 구조를 실제 저장 로직과 연결해, 상담 예약이 마이페이지와 관리자 페이지에 동시에 반영되도록 개선했습니다."

## 트러블 4. 사용자 주문 화면과 관리자 주문 화면이 서로 다른 데이터를 보는 문제

### 문제 상황

- 상품 페이지에서 주문했다고 생각했는데
- 관리자 주문 관리에는 보이지 않거나
- 관리자에서 상태를 바꿔도 사용자 화면에는 반영되지 않는 문제가 생길 수 있습니다.

### 원인

주문 화면이 더미 데이터와 로컬 저장 데이터를 섞어서 사용하면, 어느 화면은 기본 배열을 보고 어느 화면은 저장소 배열을 보는 식으로 분리됩니다.

즉, 주문 데이터도 "단일 출처"가 필요합니다.

### 해결 방법

`orderStore` 유틸을 만들어서 주문 데이터를 아래 흐름으로 통일했습니다.

- 상품 페이지에서 `addOrder()`로 저장
- 관리자 주문 관리에서 `saveOrders()`로 상태 수정
- 마이페이지에서 `loadOrders()`로 조회

즉, 사용자와 관리자가 같은 `admin_orders_v1`를 읽고 수정하도록 바꿨습니다.

### 결과

- 상품 페이지에서 바로 주문한 내용이 마이페이지에 표시됩니다.
- 관리자 주문 관리에서도 같은 주문을 확인할 수 있습니다.
- 관리자가 상태를 수정하면 사용자 주문 내역에도 같은 상태가 반영됩니다.

### 포트폴리오용 한 줄 정리

"주문 데이터 저장 방식을 공통 `orderStore`로 통합해, 사용자 주문 생성과 관리자 주문 상태 변경이 같은 저장소를 기준으로 동작하도록 개선했습니다."

## 트러블 5. DB가 없는데도 새로고침 후 상태가 유지되는 이유를 설명하기 어려운 문제

### 문제 상황

포트폴리오 면접이나 발표에서 아래 질문을 받을 수 있습니다.

- "DB가 없는데 어떻게 유지되나요?"
- "새로고침해도 왜 로그인 상태가 남아 있나요?"
- "이게 진짜 저장인가요?"

### 원인

초보자 입장에서는 "메모리 상태(state)"와 "브라우저 저장소(localStorage)"의 차이를 헷갈리기 쉽습니다.

- `useState`는 화면이 살아 있는 동안만 유지됩니다.
- `localStorage`는 브라우저에 직접 저장되기 때문에 새로고침 후에도 남습니다.

### 해결 방법

설명을 아래처럼 구분해서 정리하면 명확합니다.

- `useState`
  - 현재 화면에 즉시 보여 주기 위한 상태
- `localStorage`
  - 화면이 다시 열려도 유지해야 하는 데이터 저장소

즉, 화면은 `useState`로 그리고, 실제 기억은 `localStorage`가 맡는 구조라고 설명하면 됩니다.

### 결과

면접이나 포트폴리오 발표에서 "왜 유지되는지"를 구조적으로 설명할 수 있습니다.

### 포트폴리오용 한 줄 정리

"화면 표시 상태는 React state로 관리하고, 로그인/주문/예약처럼 유지가 필요한 데이터는 `localStorage`에 저장해 새로고침 이후에도 복원되도록 구성했습니다."

# 마무리 정리

이 프로젝트는 DB 프로그램 없이도 아래 흐름을 만들 수 있습니다.

- 회원가입
- 로그인 유지
- 상품 주문 저장
- 상담 예약 저장
- 마이페이지 조회
- 관리자 페이지 동기화

핵심은 브라우저 저장소를 공통 데이터 저장소처럼 쓰고, 모든 화면이 같은 키를 읽고 쓰게 만드는 것입니다.

실서비스 수준의 보안과 다중 사용자 동시성은 없지만, 포트폴리오에서는 "상태 저장과 화면 연동을 어떻게 설계했는지"를 보여 주기에 충분한 구조입니다.
