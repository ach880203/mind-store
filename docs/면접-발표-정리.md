# 면접 발표 정리

작성일: 2026-03-26

## 프로젝트 한 줄 소개

감정일기, 상담 예약, 상품 주문, 마이페이지, 관리자 화면을 하나의 흐름으로 연결한 멘탈케어 콘셉트의 React 포트폴리오 프로젝트입니다.

## 왜 이 프로젝트를 만들었는지

첫 프로젝트에서 단순한 소개 페이지가 아니라, 실제 서비스처럼 여러 화면이 이어지는 흐름을 직접 구현해 보고 싶었습니다.  
그래서 회원가입, 로그인, 예약, 주문, 마이페이지, 관리자 화면까지 한 프로젝트 안에서 연결하는 것을 목표로 만들었습니다.

## 주요 사용자 흐름

1. 사용자가 회원가입 또는 로그인합니다.
2. 감정일기를 작성하거나 상담을 예약하거나 상품을 주문합니다.
3. 저장된 결과를 마이페이지에서 다시 확인합니다.
4. 관리자 계정으로 로그인하면 관리자 화면에서 예약, 주문, 상품, 회원 정보를 확인합니다.

## 내가 구현한 핵심 기능

- 로그인과 회원가입 흐름
- 감정일기 작성 및 저장
- 상담 예약 저장과 마이페이지 연결
- 상품 주문 저장과 재고 반영
- 관리자 화면과 사용자 화면 분리
- 기본 테스트 복구

## 가장 신경 쓴 부분

- 여러 화면이 따로 놀지 않도록 데이터 흐름을 연결하는 부분
- 관리자와 사용자 화면을 구분하는 부분
- 포트폴리오 기준에서 치명적으로 보일 수 있는 문제를 직접 찾아 정리한 부분

## 겪었던 트러블과 해결 경험

- 한글 깨짐 가능성이 보여 문자열과 인코딩을 다시 점검했습니다.
- 관리자 화면이 보호되지 않아 라우트 가드를 추가했습니다.
- 홈 일기 저장이 특정 사용자 ID로 하드코딩되어 있어 현재 로그인 사용자 기준으로 수정했습니다.
- 주문 후 재고가 줄지 않아 재고 반영 로직을 추가했습니다.
- 기본 테스트가 깨져 있어 현재 구조에 맞는 테스트로 다시 작성했습니다.

## 아쉬운 점

- 실제 백엔드와 DB를 붙인 구조는 아닙니다.
- 인증과 데이터 저장은 포트폴리오 시연용 수준입니다.
- 실제 서비스라면 서버 기반 인증과 데이터 저장 구조가 반드시 필요합니다.

## 실제 서비스라면 다음에 확장할 방향

- 백엔드와 DB를 붙여 데이터 영속성 확보
- 서버 기반 인증과 권한 검증
- 예약 변경/취소 기능 고도화
- 장바구니와 실제 결제 흐름 추가
- 알림, 이메일, 관리자 통계 기능 확장

## 1분 발표 버전

안녕하세요. 이 프로젝트는 감정일기, 상담 예약, 상품 주문, 마이페이지, 관리자 화면을 하나의 흐름으로 연결한 멘탈케어 콘셉트의 React 프로젝트입니다.  
학원에서 만든 첫 프로젝트였지만, 단순히 화면만 만드는 데서 끝나지 않고 회원가입과 로그인 이후 예약이나 주문을 하고, 그 결과를 마이페이지와 관리자 화면까지 이어서 확인할 수 있도록 구성했습니다.  
프로젝트를 정리하면서 관리자 권한 보호, 홈 일기 저장 하드코딩, 주문 후 재고 반영, 테스트 복구 같은 문제를 직접 찾아 수정했고, 이를 통해 단순 구현을 넘어서 흐름과 구조를 보는 경험을 쌓았습니다.  
실제 서비스 수준의 백엔드까지 붙인 프로젝트는 아니지만, 프론트엔드에서 구현할 수 있는 사용자 경험과 상태 연결, 문제 해결 과정을 보여 주는 데 집중했습니다.

## 3분 발표 버전

안녕하세요. 제가 소개할 프로젝트는 감정일기, 상담 예약, 상품 주문, 마이페이지, 관리자 화면을 하나의 흐름으로 연결한 멘탈케어 콘셉트의 React 프로젝트입니다.

이 프로젝트를 만든 이유는 첫 프로젝트에서 단순한 소개형 페이지가 아니라, 실제 서비스처럼 여러 화면이 연결되는 구조를 직접 구현해 보고 싶었기 때문입니다. 그래서 회원가입과 로그인뿐 아니라 상담 예약, 상품 주문, 마이페이지, 관리자 화면까지 한 프로젝트 안에서 경험할 수 있도록 구성했습니다.

사용자 흐름은 크게 이렇습니다. 사용자가 회원가입이나 로그인을 한 뒤 감정일기를 작성하거나 상담을 예약하거나 상품을 주문합니다. 이후 그 결과를 마이페이지에서 다시 확인할 수 있고, 관리자 계정으로 로그인하면 예약, 주문, 상품, 회원 정보를 확인할 수 있습니다.

구현하면서 가장 신경 쓴 부분은 각각의 화면이 따로 노는 것이 아니라 데이터 흐름이 이어지도록 만드는 것이었습니다. 예를 들어 예약과 주문 결과가 마이페이지에서 다시 보여야 했고, 관리자 화면에서도 같은 데이터를 확인할 수 있도록 구조를 맞췄습니다.

정리 과정에서 몇 가지 중요한 문제도 발견했습니다. 관리자 페이지가 보호되지 않아 URL로 바로 접근할 수 있는 문제가 있었고, 홈 일기 저장이 특정 사용자 ID로 하드코딩되어 있었습니다. 또 주문 후 재고가 줄지 않아 사용자 입장에서 흐름이 부자연스러웠고, 기본 테스트도 실제 프로젝트와 맞지 않아 깨져 있었습니다. 그래서 관리자 라우트 가드를 추가하고, 현재 로그인 사용자 기준 저장으로 바꾸고, 주문 후 재고 반영 로직과 최소 테스트를 추가했습니다.

아쉬운 점은 실제 서비스 수준의 백엔드와 DB 구조는 아니라는 점입니다. 인증과 데이터 저장은 localStorage 기반으로 구현되어 있고, 실제 서비스라면 서버 기반 인증, 데이터베이스, 결제 시스템이 필요합니다. 다만 이 프로젝트에서는 첫 프로젝트라는 범위 안에서 프론트엔드에서 구현할 수 있는 사용자 흐름과 문제 해결 과정을 최대한 보여 주는 데 집중했습니다.

이 프로젝트를 통해 저는 화면 구현뿐 아니라, 사용자 흐름 연결, 관리자와 사용자 화면 분리, 그리고 포트폴리오 관점에서 어떤 문제가 치명적으로 보일 수 있는지까지 고민하는 경험을 할 수 있었습니다.

## 예상 질문 5개와 답변 초안

### 1. 왜 이 주제로 프로젝트를 만들었나요?

감정일기, 상담 예약, 상품 주문처럼 서로 다른 기능이 하나의 서비스 안에서 이어지는 흐름을 구현해 보고 싶었습니다. 첫 프로젝트였기 때문에 단순 화면 나열보다는, 사용자가 실제로 이동하고 데이터를 확인하는 구조를 만드는 데 집중했습니다.

### 2. 가장 신경 쓴 기능은 무엇인가요?

각 페이지를 따로 만드는 것보다, 로그인 이후 예약과 주문 결과가 마이페이지와 관리자 화면까지 이어지도록 연결하는 부분을 가장 신경 썼습니다.

### 3. 가장 어려웠던 점은 무엇이었나요?

겉으로는 화면이 많아 보여도, 실제로는 사용자 흐름이 자연스럽게 이어져야 했기 때문에 데이터 연결이 가장 어려웠습니다. 특히 관리자 보호, 하드코딩된 사용자 연결, 주문 후 재고 반영 같은 부분을 정리하면서 구조적으로 다시 보게 됐습니다.

### 4. 실제 서비스라면 무엇을 먼저 바꾸겠나요?

가장 먼저 백엔드와 DB를 붙여 데이터 영속성을 확보하고, 인증과 권한 검증을 서버 기준으로 바꾸겠습니다. 지금 구조는 포트폴리오용 프론트 프로젝트이기 때문에 localStorage 기반으로 구현돼 있습니다.

### 5. 이 프로젝트를 통해 무엇을 배웠나요?

단순히 컴포넌트를 만드는 것보다, 사용자 흐름을 끝까지 연결하는 경험이 중요하다는 점을 배웠습니다. 또 문제가 생겼을 때 UI만 보는 것이 아니라 라우트, 상태, 데이터 저장 방식까지 함께 봐야 한다는 점도 배웠습니다.

## 발표할 때 강조할 문장

- 첫 프로젝트였지만 화면만 만드는 데서 끝나지 않고 사용자 흐름 전체를 직접 연결해 보려 했습니다.
- 단순 기능 추가보다, 포트폴리오에서 치명적으로 보일 수 있는 구조 문제를 직접 찾아 정리한 경험이 있습니다.
- 실제 서비스 수준의 백엔드는 아니지만, 프론트엔드 안에서 구현 가능한 흐름과 상태 연결, 문제 해결 과정을 보여 주는 데 집중했습니다.

## 발표할 때 피해야 할 표현

- 그냥 학원에서 시켜서 만들었습니다.
- 시간이 없어서 대충 했습니다.
- 백엔드만 붙이면 완벽합니다.
- 원래는 다 하려고 했는데 못 했습니다.

## 첫 프로젝트라는 점을 강점으로 바꾸는 표현

첫 프로젝트였기 때문에 완벽한 서비스 구현보다, 여러 화면이 실제 흐름처럼 이어지도록 직접 연결해 보는 경험에 집중했습니다.

## 포트폴리오 프로젝트와 실제 서비스의 차이를 설명하는 표현

이 프로젝트는 포트폴리오 제출용 프론트엔드 프로젝트로, 실제 서비스 수준의 서버 인증과 데이터베이스 대신 프론트엔드에서 구현 가능한 흐름과 문제 해결 경험을 보여 주는 데 집중했습니다.
