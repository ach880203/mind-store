# 포트폴리오 95점 프롬프트 세트

작성일: 2026-03-26

## 1) 변경 목표

- 현재 프로젝트를 포트폴리오 제출용 기준으로 정리하기 위해, 1단계부터 3단계까지 바로 복사해서 쓸 수 있는 프롬프트 세트를 문서화한다.
- 코딩, README, 트러블슈팅, 면접 발표 준비를 단계별로 나누어 재사용 가능하게 만든다.
- 특히 2단계와 3단계는 한글, UTF-8, 설명 주석, 트러블슈팅 재사용성까지 고려한 강화 버전으로 정리한다.

## 2) 핵심 변경 요약

- 이 문서는 총 3단계로 구성된다.
- 각 단계마다 아래 4종 프롬프트가 들어 있다.
  - 코딩용
  - README 작성용
  - 트러블슈팅 문서 작성용
  - 면접 발표용
- 2단계와 3단계는 아래 공통 조건을 강하게 반영했다.
  - 모든 결과물은 포트폴리오 제출용 기준
  - 서비스 완성보다 설명력과 정리 상태를 더 중요하게 판단
  - 트러블은 나중에 트러블슈팅 문서와 면접 답변으로 재사용 가능해야 함
  - 사용자는 코드 초보이므로 코드/문서/설명 모두 쉽게 작성
  - 코드 예시는 핵심 줄마다 한글 설명 포함
  - 기존 주석은 틀린 내용이 아니라면 유지하고, 필요한 경우 한글 보완 주석만 추가

## 3) 코드/설명

## 사용 전 공통 안내

- 아래 프롬프트는 그대로 복사해서 사용해도 된다.
- 한 번에 전부 실행하지 말고 단계별로 순서대로 사용하는 편이 결과 품질이 좋다.
- 권장 순서는 `1단계 -> 2단계 -> 3단계`다.
- 코드 수정이 끝난 뒤 문서화하고, 문서화가 끝난 뒤 발표 준비로 넘어가는 흐름을 유지하는 것이 좋다.

## 1단계: 수정 계획 수립

### 목적

- 지금 프로젝트에서 무엇을 먼저 고쳐야 하는지 정리한다.
- 포트폴리오 기준에서 치명적인 문제와, 문서로 보완 가능한 부분을 구분한다.

### 1단계 코딩용 프롬프트

```text
너는 20년차 시니어 프론트엔드 개발자이자 프로젝트 매니저다.
지금부터 내가 만든 첫 프로젝트를 "실제 서비스 완성"이 아니라 "포트폴리오에서 95점 수준으로 보이게 만드는 것"을 목표로 분석해라.

중요 전제:
- 이 프로젝트는 학원에서 만든 첫 번째 프로젝트다.
- 백엔드 완성보다 프론트 프로젝트의 완성도, 설명력, 정리 상태가 더 중요하다.
- 치명적 오류, 미완성 인상, 사용자 흐름 끊김, 한글 깨짐, 문서 부족을 우선적으로 본다.

반드시 아래 순서대로 답해라.
1. 변경 목표
2. 핵심 변경 요약
3. 현재 상태 진단
4. 치명 오류
5. 포트폴리오 감점 요소
6. 트러블인지 부족한 부분인지 구분한 목록
7. 수정 우선순위 재정렬표
8. 1차 작업 계획안
9. 지금 당장 하지 않아도 되는 것

추가 조건:
- 전부 한글로 작성해라.
- 초보도 이해할 수 있게 설명하되 판단은 전문가답게 해라.
- 가능하면 파일 단위까지 구체적으로 적어라.
- 지금은 코드 수정하지 말고 계획안만 작성해라.
```

## 2단계: 코드/문서 작업 실행

### 목적

- 계획안이 정리된 뒤 실제 수정 작업을 시작한다.
- 이 단계에서는 문서와 코드 결과물이 직접 만들어져야 한다.

### 2단계 코딩용 프롬프트

```text
너는 20년차 시니어 프론트엔드 개발자이자 프로젝트 매니저다.
지금부터 현재 프로젝트를 포트폴리오 기준 95점 수준으로 보이도록 개선한다.

[프로젝트 목표]
- 이 프로젝트는 실제 서비스 완성이 아니라 포트폴리오 완성이 목표다.
- 첫 프로젝트라는 강점은 살리고, 치명적인 감점 요소를 줄이는 방향으로 수정한다.
- 지나치게 큰 리팩터링은 하지 않는다.
- 초보가 이해할 수 있는 코드 구조를 유지한다.

[반드시 지켜야 할 공통 조건]
- 화면(UI)에 표시되는 모든 문구는 반드시 한글이어야 한다.
- 기존에 한글로 되어 있는 문구를 영어로 바꾸지 마라.
- 모든 결과물은 한글이어야 한다.
- 한글 깨짐이 없어야 한다.
- 파일 인코딩은 UTF-8 기준으로 유지한다고 가정하고 작업해라.
- 한글이 깨질 가능성이 있는 문자열, 주석, 데이터 파일, 메타 태그를 항상 점검해라.
- 기존 주석은 틀린 내용이 아니라면 삭제하지 마라.
- 기존 주석이 부족하면 옆에 한글 설명 주석을 추가해라.
- 사용자는 코드 초보다. 따라서 작성되는 모든 핵심 코드에는 "왜 이렇게 바꾸는지" 알 수 있는 한글 설명 주석을 달아라.
- 코드 주석은 구현 의도, 주의점, 깨질 수 있는 포인트를 초보 기준으로 설명해야 한다.

[이번 작업 범위]
- 한글 깨짐 수정
- 관리자 접근 보호
- 홈 일기 사용자 하드코딩 제거
- 테스트 최소 복구
- 미완성 페이지 처리
- 로그인/회원가입/주문/예약 핵심 오류 정리

[작업 방식]
반드시 아래 순서로 진행해라.

1. 지금 작업할 범위를 짧게 정리
2. 수정 대상 파일 목록 제시
3. 변경 이유 설명
4. 실제 코드 수정
5. 수정 후 검증 방법 정리
6. 남은 리스크 정리

[추가 작업 원칙]
- 한 번에 다 하지 말고 우선순위 높은 묶음부터 처리해라.
- 각 묶음이 끝날 때마다 무엇이 해결됐는지 짧게 정리해라.
- 변경 이유와 영향 범위를 반드시 설명해라.
- 트러블과 부족한 부분을 구분해서 다뤄라.
- 트러블로 분류한 문제는 포트폴리오용 트러블슈팅 문서로 재사용할 수 있도록 수정 근거를 남겨라.
- 가능하면 "수정 전 문제", "수정 후 기대 효과"를 함께 설명해라.

[출력 형식]
1. 변경 목표
2. 핵심 변경 요약
3. 이번 작업 범위
4. 수정 대상 파일
5. 변경 이유
6. 실제 코드 수정
7. 검증 방법
8. 남은 리스크
9. 트러블슈팅으로 문서화할 수 있는 포인트
```

### 2단계 트러블슈팅 문서 작성용 프롬프트

```text
너는 기술 블로그와 포트폴리오용 트러블슈팅 문서를 잘 쓰는 시니어 개발자다.
현재 프로젝트에서 실제로 가치 있는 트러블슈팅 문서를 작성해라.

[문서 목표]
- 단순히 "에러가 났다" 수준이 아니라,
- 문제 상황, 원인 분석, 해결 과정, 결과, 배운 점이 드러나는 문서를 만든다.
- 포트폴리오에서 "문제를 분석하고 해결한 사람"처럼 보이게 만든다.

[가장 중요한 공통 조건]
- 전부 한글로 작성해라.
- 한글 깨짐이 없어야 한다.
- 문서는 초보도 이해할 수 있게 써라.
- 단순 요약보다 "왜 그렇게 판단했는지"가 보여야 한다.
- 블로그에 올려도 될 정도로 자연스럽게 작성해라.
- 트러블은 반드시 육하원칙이 보이게 정리해라.
- 즉, 누가/언제/어디서/무엇을/왜/어떻게의 흐름이 자연스럽게 드러나야 한다.
- 각 문서에는 반드시 "원인 - 과정 - 결과"가 명확히 있어야 한다.
- 가능한 경우 수정 전 코드와 수정 후 코드를 실물로 넣어 비교해라.
- 코드 예시는 사용자가 이해할 수 있도록 한글 설명을 붙여라.
- 기존 주석은 틀린 것이 아니면 삭제하지 않는 방향을 유지해라.

[우선 작성 대상]
- 한글 깨짐 또는 인코딩 문제
- 관리자 권한 보호/라우팅 문제
- 로컬스토리지 기반 데이터 연결 문제
- 테스트 깨짐 복구 과정

[반드시 따를 문서 구조]
1. 문제 상황
2. 언제, 어디서, 어떤 문제가 발생했는지
3. 왜 문제가 생겼는지
4. 처음에 했던 잘못된 접근
5. 원인을 어떻게 좁혀갔는지
6. 해결 방법
7. 수정 전 코드
8. 수정 후 코드
9. 해결 후 달라진 점
10. 이번 경험으로 배운 점

[추가 조건]
- 사소한 버그 나열처럼 쓰지 마라.
- 포트폴리오에서 가치가 높은 문제 중심으로 작성해라.
- "부족한 기능"과 "실제 트러블"을 혼동하지 마라.
- 문서 끝에는 면접에서 이 트러블을 어떻게 설명하면 좋은지도 짧게 덧붙여라.

[출력 형식]
1. 변경 목표
2. 핵심 변경 요약
3. 트러블슈팅 문서 본문
4. 면접/발표에서 이 문서를 활용하는 방법
```

### 2단계 면접 발표용 프롬프트

```text
너는 개발자 포트폴리오 발표 코치다.
현재 프로젝트를 기준으로 면접 또는 포트폴리오 발표에서 바로 사용할 수 있는 발표 자료 초안을 작성해라.

[목표]
- 첫 프로젝트임에도 구조적으로 설명할 수 있는 사람처럼 보이게 만든다.
- 단순히 "만들었다"가 아니라 "왜 만들었고, 무엇을 고민했고, 어떤 문제를 해결했는지"를 말할 수 있게 한다.

[반드시 지켜야 할 공통 조건]
- 전부 한글로 작성해라.
- 발표문에 한글 깨짐이 없어야 한다.
- 과장 없이 명확하게 작성해라.
- 초보 프로젝트지만 생각이 정리된 사람처럼 들리게 작성해라.
- 실제 서비스가 아니라 포트폴리오 프로젝트라는 점을 전략적으로 설명해라.
- 트러블로 분류한 문제는 "원인 - 해결 과정 - 결과"가 보이게 설명해라.
- 발표 내용은 README와 트러블슈팅 문서 내용과 연결될 수 있어야 한다.

[반드시 포함할 항목]
1. 프로젝트 한 줄 소개
2. 왜 이 프로젝트를 만들었는지
3. 주요 사용자 흐름
4. 내가 구현한 핵심 기능
5. 가장 신경 쓴 부분
6. 겪었던 트러블과 해결 경험
7. 아쉬운 점
8. 실제 서비스라면 다음에 확장할 방향

[추가 요구]
- 1분 버전
- 3분 버전
- 예상 질문 5개와 답변 초안
- 첫 프로젝트라는 점을 강점으로 바꾸는 한 문장
- 포트폴리오 프로젝트와 실제 서비스의 차이를 설명하는 한 문장

[출력 형식]
1. 변경 목표
2. 핵심 변경 요약
3. 1분 발표 버전
4. 3분 발표 버전
5. 예상 질문 5개와 답변 초안
6. 발표할 때 강조할 문장
7. 발표할 때 피해야 할 표현
```

## 3단계: 발표/면접 마감 정리

### 목적

- 수정한 결과물을 최종 점검하고, 제출/발표 직전 상태로 다듬는다.
- 이 단계에서는 "무엇을 더 만들까"보다 "어떻게 더 잘 보여줄까"가 중요하다.

### 3단계 코딩용 프롬프트

```text
너는 시니어 프론트엔드 개발자이자 프로젝트 QA 리더이자 포트폴리오 최종 검수자다.
현재 프로젝트를 포트폴리오 제출 직전 상태라고 생각하고, 최종 점검 체크리스트와 마지막 보완 포인트를 작성해라.

[최종 목표]
- 지금 상태에서 제출하거나 발표해도 민망하지 않도록 마지막 감점 요소를 제거한다.
- 서비스 완성보다 제출용 완성도와 설명 가능성을 더 중요하게 본다.

[반드시 지켜야 할 공통 조건]
- 전부 한글로 작성해라.
- 화면 문구, 문서 문구, 발표 문구 모두 한글 깨짐이 없어야 한다.
- 판단 기준은 "실서비스 수준"이 아니라 "포트폴리오 제출 기준"이어야 한다.
- 사용자는 코드 초보다. 따라서 체크리스트와 보완 포인트도 이해하기 쉽게 작성해라.
- 트러블로 분류된 항목은 최종적으로 트러블슈팅 문서와 발표 답변으로 연결 가능한지 점검해라.

[반드시 포함할 항목]
1. 최종 점검 목표
2. 제출 전 반드시 확인할 항목
3. 화면 기준 점검 항목
4. 기능 기준 점검 항목
5. 문서 기준 점검 항목
6. 발표 전 점검 항목
7. 남아 있어도 괜찮은 한계
8. 지금 남아 있으면 위험한 문제
9. 최종적으로 가장 먼저 고칠 마지막 3개

[추가 요구]
- "수정해야 할 것"과 "문서로 설명해도 되는 것"을 구분해라.
- 체크리스트는 실제로 하나씩 체크할 수 있는 문장으로 작성해라.
- 마지막에는 "제출 직전 10분 점검표"도 짧게 만들어라.

[출력 형식]
1. 변경 목표
2. 핵심 변경 요약
3. 최종 점검 체크리스트
4. 마지막 보완 우선순위
5. 제출 직전 10분 점검표
```

### 3단계 README 작성용 프롬프트

```text
너는 포트폴리오 문서 최종 검수자이자 기술 글 편집자다.
현재 README 초안을 최종 제출용으로 다듬는 기준과 수정 포인트를 제시해라.

[목표]
- README가 길기만 한 문서가 아니라, 빠르게 읽히고 인상이 좋은 문서가 되게 만든다.
- 초보 프로젝트지만 생각과 개선 의도가 정리된 문서처럼 보이게 만든다.

[반드시 지켜야 할 공통 조건]
- 전부 한글로 작성해라.
- README 문장에 한글 깨짐이 없어야 한다.
- 과장된 표현은 줄이고, 실제로 구현한 범위와 고민한 지점을 중심으로 정리해라.
- 사용자는 코드 초보이므로, 문장 구조도 쉽게 읽히게 다듬어라.

[반드시 포함할 항목]
1. README 최종 점검 기준
2. 꼭 줄여야 할 부분
3. 꼭 더 강조해야 할 부분
4. 초보 프로젝트답게 솔직하게 남겨야 할 문장
5. 포트폴리오 점수를 올리는 표현 방식
6. 최종 검수 체크리스트
7. README 마지막에 넣기 좋은 마무리 문장

[추가 요구]
- README가 너무 변명처럼 보이지 않게 조정해라.
- "한계 인정"과 "성장 포인트"의 균형을 맞춰라.
- README와 트러블슈팅 문서, 발표 내용이 서로 어긋나지 않는지도 함께 보라.

[출력 형식]
1. 변경 목표
2. 핵심 변경 요약
3. README 최종 검수 기준
4. 수정 권장 포인트
5. 최종 검수 체크리스트
6. 추천 마무리 문장
```

### 3단계 트러블슈팅 문서 작성용 프롬프트

```text
너는 기술 문서 편집자이자 개발 블로그 코치이자 면접 대비 코치다.
작성한 트러블슈팅 문서가 포트폴리오와 면접에서 모두 가치 있게 쓰일 수 있는지 최종 검수해라.

[목표]
- 단순한 문제 기록이 아니라, 문제 해결 능력이 드러나는 문서인지 확인한다.
- 문서가 블로그용, 포트폴리오용, 면접 답변용으로 재사용 가능한 상태인지 점검한다.

[반드시 지켜야 할 공통 조건]
- 전부 한글로 작성해라.
- 한글 깨짐이 없어야 한다.
- "무슨 에러가 났다"보다 "어떻게 원인을 좁히고 해결했는가"가 중심이어야 한다.
- 사용자는 코드 초보다. 따라서 문서 설명도 쉽게 읽히게 다듬어라.
- 수정 전 코드와 수정 후 코드가 있다면, 초보도 이해할 수 있도록 설명이 충분한지 함께 점검해라.

[반드시 포함할 항목]
1. 좋은 트러블슈팅 문서의 기준
2. 현재 문서에서 부족할 수 있는 부분
3. 더 보강해야 할 설명 포인트
4. 초보다운 시행착오를 강점으로 바꾸는 표현
5. 면접에서 재사용하기 좋은 문장
6. 최종 문서 체크리스트

[추가 요구]
- 문제 상황이 육하원칙으로 자연스럽게 보이는지 점검해라.
- 원인 - 과정 - 결과 흐름이 끊기지 않는지 봐라.
- 트러블과 단순 기능 부족을 혼동하는 문장이 있다면 바로잡아라.

[출력 형식]
1. 변경 목표
2. 핵심 변경 요약
3. 트러블슈팅 문서 최종 검수 기준
4. 보강 포인트
5. 면접 재사용 문장
6. 최종 체크리스트
```

### 3단계 면접 발표용 프롬프트

```text
너는 개발자 면접 발표 코치이자 포트폴리오 스토리텔링 전문가다.
현재 프로젝트 발표문과 예상 질문 답변을 최종 점검하고, 실전 발표용으로 다듬어라.

[목표]
- 발표가 길어지지 않고, 질문이 들어와도 흔들리지 않는 상태로 만든다.
- 첫 프로젝트라는 점을 약점이 아니라 성장 가능성과 학습 태도로 연결해 보이게 만든다.

[반드시 지켜야 할 공통 조건]
- 전부 한글로 작성해라.
- 발표 문장에 한글 깨짐이 없어야 한다.
- 솔직하되 약해 보이지 않게 표현해라.
- README와 트러블슈팅 문서의 내용과 어긋나지 않게 정리해라.
- 트러블로 분류한 항목은 원인 - 해결 과정 - 결과가 드러나게 말할 수 있어야 한다.

[반드시 포함할 항목]
1. 면접 발표 최종 목표
2. 1분 소개에서 꼭 남겨야 할 문장
3. 3분 설명에서 반드시 들어가야 할 구조
4. 질문이 들어왔을 때 흔들리기 쉬운 포인트
5. 이를 방어하는 답변 방식
6. 말하지 않는 편이 나은 내용
7. 최종 발표 체크리스트
8. 첫 프로젝트라는 점을 강점으로 바꾸는 최종 표현
9. 포트폴리오 프로젝트와 실제 서비스의 차이를 설명하는 최종 표현

[추가 요구]
- 예상 질문이 들어왔을 때 20초 안에 답하는 버전도 짧게 제시해라.
- 너무 겸손해서 약해 보이는 표현과, 너무 과장해서 위험한 표현을 구분해라.
- 마지막에는 발표 직전 읽을 수 있는 "30초 마음 정리 문장"도 넣어라.

[출력 형식]
1. 변경 목표
2. 핵심 변경 요약
3. 1분 발표 최종본
4. 3분 발표 최종본
5. 흔들리기 쉬운 질문과 방어 답변
6. 말하지 않는 편이 나은 표현
7. 최종 발표 체크리스트
8. 발표 직전 30초 정리 문장
```

## 빠른 사용 예시

### 예시 1: 지금 코드부터 고치고 싶을 때

1. 2단계 코딩용 프롬프트 사용
2. 수정된 코드 결과 확인
3. 남은 리스크 정리 확인

### 예시 2: 코드 수정 후 README를 바로 만들고 싶을 때

1. 2단계 README 작성용 프롬프트 사용
2. README 초안 생성
3. 3단계 README 작성용 프롬프트로 최종 다듬기

### 예시 3: 트러블슈팅 문서를 포트폴리오와 면접에 같이 쓰고 싶을 때

1. 2단계 트러블슈팅 문서 작성용 프롬프트 사용
2. 수정 전/수정 후 코드가 포함된 문서 생성
3. 3단계 트러블슈팅 문서 작성용 프롬프트로 최종 검수

### 예시 4: 발표 준비까지 이어가고 싶을 때

1. 2단계 면접 발표용 프롬프트 사용
2. 1분/3분 발표문 작성
3. 3단계 면접 발표용 프롬프트로 실전 발표 수준까지 마감

## 4) 확인 방법

### 문서 활용 방법

1. [포트폴리오-95점-프롬프트-세트.md](C:/Programmer/Work/mind-store/docs/포트폴리오-95점-프롬프트-세트.md)를 연다.
2. 지금 필요한 단계의 프롬프트만 복사해서 사용한다.
3. 한 번에 전부 하지 말고 단계별 결과를 확인한 뒤 다음 단계로 넘어간다.

### 추천 시작 순서

1. 1단계 코딩용 프롬프트
2. 2단계 코딩용 프롬프트
3. 2단계 README 작성용 프롬프트
4. 2단계 트러블슈팅 문서 작성용 프롬프트
5. 2단계 면접 발표용 프롬프트
6. 3단계 최종 검수 프롬프트들

### 완료 기준

- 1단계부터 3단계까지 단계별 프롬프트가 정리되어 있다.
- 2단계와 3단계는 강화 조건이 포함되어 있다.
- 코드 수정, README, 트러블슈팅, 면접 발표 준비가 한 흐름으로 이어진다.
- 초보 프로젝트의 강점을 살리면서도 포트폴리오 제출용으로 바로 활용 가능하다.
