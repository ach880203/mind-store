# 마음상점 포트폴리오 최종 작성본

작성일: 2026-03-30

## 1. 프로젝트 한 줄 소개

감정일기, 상담 예약, 상품 주문, 마이페이지, 관리자 화면을 하나의 흐름으로 연결한 멘탈케어 콘셉트의 React 프론트엔드 프로젝트입니다.

## 2. 프로젝트 개요

이 프로젝트는 학원에서 진행한 첫 번째 프로젝트를 바탕으로, 포트폴리오 제출용 기준에 맞게 다시 정리한 결과물입니다.  
단순히 화면만 여러 개 만드는 것이 아니라, 사용자가 회원가입하고 로그인한 뒤 상담을 예약하거나 상품을 주문하고, 마이페이지에서 내역을 확인하는 흐름까지 직접 연결해 본 점이 핵심입니다.

첫 프로젝트였기 때문에 실제 서비스 수준의 백엔드 구축보다는, 프론트엔드에서 구현할 수 있는 사용자 흐름과 화면 완성도, 그리고 데이터 연결 경험을 쌓는 데 집중했습니다.

## 3. 제작 배경과 목적

- React 기반으로 여러 페이지가 이어지는 서비스 흐름을 끝까지 구현해 보고 싶었습니다.
- 사용자 화면뿐 아니라 관리자 화면까지 함께 구성해 보면서, 데이터가 여러 화면에서 어떻게 이어지는지 직접 경험하고 싶었습니다.
- 첫 프로젝트인 만큼 복잡한 기술보다 기본기를 확인할 수 있는 흐름 설계와 화면 완성도에 집중했습니다.

## 4. 프로젝트 목표

- 회원가입, 로그인, 예약, 주문, 마이페이지까지 이어지는 사용자 흐름 구현
- 관리자와 일반 사용자 화면 분리
- localStorage 기반 데이터 저장과 상태 유지
- 포트폴리오 제출용 기준에서 치명적인 약점 정리
- README, 트러블슈팅, 발표 자료까지 설명 가능한 프로젝트로 완성

## 7. 사용자 흐름

1. 사용자가 회원가입 또는 로그인합니다.
2. 감정일기를 작성하거나 상담을 예약하거나 상품을 주문합니다.
3. 저장된 결과는 마이페이지에서 다시 확인할 수 있습니다.
4. 관리자 계정으로 로그인하면 관리자 화면에서 예약, 주문, 상품, 회원 정보를 확인할 수 있습니다.

### 한 줄 흐름 요약

회원가입 → 로그인 → 감정일기 / 상담 예약 / 상품 주문 → 마이페이지 확인 → 관리자 기능 분리

## 8. 구현하며 신경 쓴 포인트

### 1. 사용자 흐름 연결

로그인, 예약, 주문, 마이페이지가 각각 따로 노는 화면이 아니라, 하나의 서비스처럼 이어지도록 연결했습니다.

### 2. 관리자와 사용자 화면 분리

일반 사용자 화면과 관리자 화면을 나누고, 관리자 라우트는 로그인과 권한 조건을 확인하도록 정리했습니다.

### 3. 초보도 이해할 수 있는 구조 유지

지나치게 복잡한 구조로 바꾸기보다, 초보가 읽어도 이해할 수 있는 코드 흐름을 유지하면서 치명적인 약점부터 보완하는 방향으로 개선했습니다.

### 4. 포트폴리오 기준 품질 보강

- 관리자 접근 보호
- 홈 일기 저장 사용자 하드코딩 제거
- 주문 후 재고 반영
- 예약 중복 방지
- 테스트 복구
- 한글 문구 및 인코딩 정리

## 9. 프로젝트 강점

- 첫 프로젝트인데도 기능 범위가 넓습니다.
- 사용자 화면과 관리자 화면을 함께 구현했습니다.
- 단순 UI가 아니라 예약/주문/일기 내역을 마이페이지와 연결했습니다.
- 포트폴리오 관점에서 치명적인 문제를 직접 점검하고 수정한 경험이 있습니다.

## 10. 트러블슈팅 요약

### 1. 관리자 페이지 접근 보호 문제

- 문제: 관리자 페이지가 별도 보호 없이 열릴 수 있었습니다.
- 원인: 라우트 레벨 권한 분기 로직이 부족했습니다.
- 해결: 로그인 여부와 관리자 권한을 확인하는 라우트 가드를 추가했습니다.
- 결과: 사용자와 관리자 흐름이 명확하게 분리되었습니다.

### 2. 홈 일기 저장 사용자 하드코딩 문제

- 문제: 특정 사용자 ID 기준으로 저장되는 하드코딩이 있었습니다.
- 원인: 현재 로그인 사용자 기준 저장 로직이 연결되지 않았습니다.
- 해결: 현재 로그인 사용자 정보를 기준으로 저장되도록 수정했습니다.
- 결과: 마이페이지와 감정일기 데이터 연결 신뢰도가 높아졌습니다.

### 3. 주문 후 재고 미반영 문제

- 문제: 주문은 되지만 재고가 줄지 않아 흐름이 어색했습니다.
- 원인: 주문 저장과 상품 상태 갱신이 분리되어 있었습니다.
- 해결: 주문 시 재고를 차감하고 상태를 함께 갱신하도록 수정했습니다.
- 결과: 주문 이후 상품 상태 변화가 사용자에게 보이게 되었습니다.

### 4. 예약 중복 방지 부족 문제

- 문제: 같은 날짜/시간 예약을 중복으로 넣을 수 있었습니다.
- 원인: 예약 저장 전에 같은 시간대 확인 로직이 없었습니다.
- 해결: 이미 예약된 시간은 비활성화하고 저장 단계에서도 중복을 검사했습니다.
- 결과: 예약 흐름의 신뢰도가 높아졌습니다.

### 5. 테스트 실패 문제

- 문제: 기본 테스트가 현재 프로젝트 구조와 맞지 않아 실패했습니다.
- 원인: CRA 예제 테스트가 그대로 남아 있었습니다.
- 해결: 현재 구조에 맞는 저장/재고 관련 테스트로 교체했습니다.
- 결과: `npm test -- --watchAll=false` 기준 테스트가 통과하도록 정리했습니다.

## 11. 트러블과 부족한 부분 구분

### 트러블

- 관리자 접근 보호 부재
- 사용자 기준 데이터 저장 불안정

### 부족한 부분

- 백엔드/DB 미구축

- 장바구니 없음
- 비밀번호 찾기 없음
- 서버 기반 인증 없음
- 관리자 고급 기능 부족

## 12. 아쉬운 점

- 실제 백엔드와 데이터베이스를 붙인 구조는 아닙니다.
- 인증과 데이터 저장은 포트폴리오 시연용으로 localStorage 기반으로 구현했습니다.
- 실제 서비스 수준의 결제, 보안, 서버 검증 구조까지는 포함하지 못했습니다.

## 13. 실제 서비스라면 확장할 방향

- 백엔드와 DB를 붙여 데이터 영속성 확보
- 서버 기반 인증과 권한 검증
- 예약 변경/취소 기능 고도화
- 장바구니와 실제 결제 흐름 추가
- 알림, 이메일, 관리자 통계 기능 확장

## 14. 포트폴리오 프로젝트와 실제 서비스의 차이

이 프로젝트는 포트폴리오 제출용 프론트엔드 프로젝트입니다.  
즉, 실제 서비스 수준의 인증 서버, 결제 시스템, 데이터베이스를 붙여 완성한 형태는 아니며, 대신 프론트엔드에서 구현할 수 있는 사용자 흐름과 화면 구조, 상태 연결, 문제 해결 경험을 보여 주는 데 집중했습니다.

이 프로젝트를 만든 이유는 첫 프로젝트에서 단순한 소개형 페이지가 아니라, 실제 서비스처럼 여러 화면이 이어지는 구조를 직접 구현해 보고 싶었기 때문입니다.  
그래서 회원가입과 로그인뿐 아니라 상담 예약, 상품 주문, 마이페이지, 관리자 화면까지 한 프로젝트 안에서 경험할 수 있도록 구성했습니다.

사용자 흐름은 크게 이렇습니다.  
사용자가 회원가입이나 로그인을 한 뒤 감정일기를 작성하거나 상담을 예약하거나 상품을 주문합니다.  
이후 그 결과를 마이페이지에서 다시 확인할 수 있고, 관리자 계정으로 로그인하면 예약, 주문, 상품, 회원 정보를 확인할 수 있습니다.

구현하면서 가장 신경 쓴 부분은 각각의 화면이 따로 노는 것이 아니라 데이터 흐름이 이어지도록 만드는 것이었습니다.  
예를 들어 예약과 주문 결과가 마이페이지에서 다시 보여야 했고, 관리자 화면에서도 같은 데이터를 확인할 수 있도록 구조를 맞췄습니다.

정리 과정에서 몇 가지 중요한 문제도 발견했습니다.  
관리자 페이지가 보호되지 않아 URL로 바로 접근할 수 있는 문제가 있었고, 일부 저장 로직은 사용자 기준 연결이 불안정했습니다.  
또 주문 후 재고가 줄지 않거나 예약이 중복될 수 있는 부분, 테스트가 현재 구조와 맞지 않는 부분도 있었습니다.  
그래서 관리자 라우트 가드를 추가하고, 현재 로그인 사용자 기준 저장으로 바꾸고, 주문 후 재고 반영과 예약 중복 방지, 테스트 복구까지 진행했습니다.

아쉬운 점은 실제 서비스 수준의 백엔드와 DB 구조는 아니라는 점입니다.  
인증과 데이터 저장은 localStorage 기반으로 구현되어 있고, 실제 서비스라면 서버 기반 인증, 데이터베이스, 결제 시스템이 필요합니다.  
다만 이 프로젝트에서는 첫 프로젝트라는 범위 안에서 프론트엔드에서 구현할 수 있는 사용자 흐름과 문제 해결 과정을 최대한 보여 주는 데 집중했습니다.

이 프로젝트를 통해 저는 화면 구현뿐 아니라 사용자 흐름 연결, 관리자와 사용자 화면 분리, 그리고 포트폴리오 관점에서 어떤 문제가 치명적으로 보일 수 있는지까지 고민하는 경험을 할 수 있었습니다.

## 20. 예상 질문과 답변 초안

### 1. 왜 이 주제로 프로젝트를 만들었나요?

감정일기, 상담 예약, 상품 주문처럼 서로 다른 기능이 하나의 서비스 안에서 이어지는 흐름을 구현해 보고 싶었습니다.  
첫 프로젝트였기 때문에 단순 화면 나열보다, 사용자가 실제로 이동하고 데이터를 확인하는 구조를 만드는 데 집중했습니다.

### 2. 가장 신경 쓴 기능은 무엇인가요?

각 페이지를 따로 만드는 것보다, 로그인 이후 예약과 주문 결과가 마이페이지와 관리자 화면까지 이어지도록 연결하는 부분을 가장 신경 썼습니다.

### 3. 가장 어려웠던 점은 무엇이었나요?

겉으로는 화면이 많아 보여도, 실제로는 사용자 흐름이 자연스럽게 이어져야 했기 때문에 데이터 연결이 가장 어려웠습니다.  
특히 관리자 보호, 사용자 기준 저장, 주문 후 재고 반영 같은 부분을 정리하면서 구조적으로 다시 보게 됐습니다.

### 4. 실제 서비스라면 무엇을 먼저 바꾸겠나요?

가장 먼저 백엔드와 DB를 붙여 데이터 영속성을 확보하고, 인증과 권한 검증을 서버 기준으로 바꾸겠습니다.  
지금 구조는 포트폴리오용 프론트 프로젝트이기 때문에 localStorage 기반으로 구현돼 있습니다.

### 5. 이 프로젝트를 통해 무엇을 배웠나요?

단순히 컴포넌트를 만드는 것보다, 사용자 흐름을 끝까지 연결하는 경험이 중요하다는 점을 배웠습니다.  
또 문제가 생겼을 때 UI만 보는 것이 아니라 라우트, 상태, 데이터 저장 방식까지 함께 봐야 한다는 점도 배웠습니다.

## 21. 발표할 때 강조할 문장

- 첫 프로젝트였지만 화면만 만드는 데서 끝나지 않고 사용자 흐름 전체를 직접 연결해 보려 했습니다.
- 단순 기능 추가보다, 포트폴리오에서 치명적으로 보일 수 있는 구조 문제를 직접 찾아 정리한 경험이 있습니다.
- 실제 서비스 수준의 백엔드는 아니지만, 프론트엔드 안에서 구현 가능한 흐름과 상태 연결, 문제 해결 과정을 보여 주는 데 집중했습니다.
