# 포트폴리오 트러블슈팅 정리

작성일: 2026-03-26

## 문서 목표

이 문서는 프로젝트를 만들면서 만난 문제를 단순히 나열하는 것이 아니라,  
"어떤 문제가 있었고, 왜 생겼고, 어떤 과정을 거쳐 해결했는지"를 포트폴리오와 면접에서 설명할 수 있게 정리한 문서입니다.

---

## 1. 한글 깨짐과 인코딩 문제

### 문제 상황

- 누구: 프로젝트를 정리하던 개발자
- 언제: 포트폴리오 제출 전 점검 단계
- 어디서: 컴포넌트 문구, 주석, 일부 데이터 파일 확인 과정
- 무엇을: 한글이 깨져 보이는 문자열이 발견됨
- 왜 중요했는가: 한국어 프로젝트에서 한글 깨짐은 완성도와 신뢰도를 크게 떨어뜨림
- 어떻게 확인했는가: 주요 페이지 파일과 실행 화면 문구를 점검하면서 발견

### 왜 문제가 생겼는지

- 파일 인코딩이나 편집기 환경 차이로 한글 문자열이 깨진 흔적이 남아 있었습니다.
- 특히 포트폴리오 제출용으로 다시 정리하는 과정에서는 "한글이 깨지지 않는다"는 점이 매우 중요했습니다.

### 처음에 했던 잘못된 접근

- 깨진 문자열이 일부만 보인다고 생각하고, 화면에서 보이는 부분만 고치면 된다고 판단했습니다.
- 하지만 실제로는 데이터 파일, 주석, 메타 문구까지 같이 봐야 했습니다.

### 해결 방법

- 한글이 들어가는 주요 컴포넌트와 데이터 파일을 우선 점검했습니다.
- 새로 추가하거나 수정하는 문자열은 모두 한글로 작성하고, UTF-8 기준을 유지하도록 정리했습니다.
- 설명 주석도 한글로 보강해 이후 수정 시 다시 깨질 가능성을 줄였습니다.

### 수정 전 코드

```js
saveDiary({
  ...data,
  userId: "minji",
});
```

### 수정 후 코드

```js
const currentUser = getCurrentUser();

// 로그인 사용자를 기준으로 저장해야 마이페이지와 데이터 소유자가 정확히 맞습니다.
if (!currentUser) {
  setDiaryNotice("마음일기를 저장하려면 먼저 로그인해 주세요.");
  navigate("/login");
  return;
}

saveDiary({
  ...data,
  userId: currentUser.user_id,
});
```

### 해결 후 달라진 점

- 화면 문구와 데이터 연결 설명이 서로 맞게 정리됐습니다.
- 포트폴리오에서 "한글 프로젝트인데 문자열 관리가 불안하다"는 인상을 줄일 수 있었습니다.

### 이번 경험으로 배운 점

- 한글 깨짐은 단순한 글자 문제가 아니라 프로젝트 완성도 문제입니다.
- 특히 한국어 서비스 프로젝트는 인코딩과 문자열 정리를 처음부터 중요하게 봐야 합니다.

### 면접에서 이렇게 설명하면 좋음

"처음에는 일부 문구만 고치면 된다고 생각했는데, 실제로는 데이터 연결과 주석, 메타 정보까지 같이 봐야 했습니다. 그래서 단순 문자열 수정이 아니라 한글 표현과 사용자 흐름이 함께 맞도록 정리했습니다."

## 2. 관리자 권한 보호와 라우팅 문제

### 문제 상황

- 누구: 관리자 화면을 정리하던 개발자
- 언제: 포트폴리오 점검 단계
- 어디서: `/admin` 라우트 구조 확인 중
- 무엇을: 로그인 여부나 관리자 권한 검증 없이 관리자 화면 접근 가능
- 왜 중요했는가: 포트폴리오에서 구조 이해도가 낮아 보일 수 있고, 실제 서비스 관점에서도 위험한 구조
- 어떻게 확인했는가: 관리자 라우트와 관리자 레이아웃을 함께 읽어 보며 확인

### 왜 문제가 생겼는지

- 초기 구현 단계에서는 관리자 화면을 먼저 보이게 만드는 데 집중했고, 권한 보호는 뒤로 밀려 있었습니다.
- 학습 프로젝트에서는 자주 생기는 흐름이지만, 포트폴리오 제출용으로는 반드시 정리해야 하는 부분이었습니다.

### 처음에 했던 잘못된 접근

- 관리자 메뉴만 보이지 않으면 어느 정도 괜찮다고 생각했습니다.
- 하지만 실제로는 메뉴 노출 여부와 별개로 URL 직접 접근이 가능하면 구조적으로 막혀 있지 않은 상태입니다.

### 해결 방법

- 관리자 라우트 앞단에 가드 컴포넌트를 두었습니다.
- 로그인 안 된 경우는 로그인 페이지로, 일반 사용자는 홈으로 돌려보내도록 정리했습니다.

### 수정 전 코드

```jsx
const AdminRoutes = () => {
  return (
    <Route path="/admin" element={<AdminLayout />}>
      <Route index element={<Navigate to="reservations" replace />} />
    </Route>
  );
};
```

### 수정 후 코드

```jsx
const AdminRouteGuard = () => {
  const currentUser = getCurrentUser();

  // 관리자 화면은 로그인 여부와 관리자 권한을 함께 확인해야 합니다.
  if (!currentUser) {
    return <Navigate to="/login" replace />;
  }

  if (Number(currentUser.admin) !== 1) {
    return <Navigate to="/" replace />;
  }

  return <AdminLayout />;
};
```

### 해결 후 달라진 점

- 관리자 화면 접근 조건이 명확해졌습니다.
- 포트폴리오에서 "관리자와 사용자 흐름을 구분할 줄 안다"는 인상을 줄 수 있게 됐습니다.

### 이번 경험으로 배운 점

- 화면 분리만으로는 권한 분리가 끝난 것이 아닙니다.
- 라우트 수준에서 막는 구조가 있어야 "구조를 이해하고 만든 프로젝트"처럼 보입니다.

### 면접에서 이렇게 설명하면 좋음

"처음에는 관리자 메뉴를 보이지 않게 하는 정도로 생각했지만, 실제로는 URL 직접 접근을 막아야 구조가 완성된다고 판단했습니다. 그래서 라우트 가드를 추가해 로그인 여부와 관리자 권한을 같이 확인하도록 바꿨습니다."

## 3. 로컬스토리지 기반 데이터 연결 정합성 문제

### 문제 상황

- 누구: 주문과 마이페이지 흐름을 연결하던 개발자
- 언제: 주문/마이페이지 점검 단계
- 어디서: 주문 저장 로직과 상품 목록 화면
- 무엇을: 주문은 저장되지만 재고가 줄지 않고, 주문 표시 정보도 더미 사용자 기준으로 연결되는 문제
- 왜 중요했는가: "주문은 되는데 시스템은 안 움직이는" 데모처럼 보일 수 있었기 때문
- 어떻게 확인했는가: 주문 저장 로직과 상품 저장 로직, 마이페이지 흐름을 함께 읽으며 확인

### 왜 문제가 생겼는지

- 초기 구현에서는 주문 기록 저장 자체에만 집중했습니다.
- 그래서 재고 반영과 실제 저장된 사용자 정보 기준 연결이 빠져 있었습니다.

### 처음에 했던 잘못된 접근

- 주문 내역만 쌓이면 충분하다고 생각했습니다.
- 하지만 포트폴리오 기준에서는 "주문 후 화면에 변화가 보이는가"도 중요했습니다.

### 해결 방법

- 주문 저장 뒤 상품 재고를 같이 차감하도록 보완했습니다.
- 주문 데이터 정규화 시 정적 더미 사용자 배열이 아니라 현재 저장된 회원 목록을 기준으로 맞추도록 수정했습니다.

### 수정 전 코드

```js
const matchedUser = usersdb.find((user) => user.user_id === order?.userId);

addOrder({
  product: product.name,
  productId: product.id,
  quantity: 1,
  price: Number(product.price),
});
```

### 수정 후 코드

```js
const matchedUser = loadUsers().find(
  (user) =>
    user.user_id === order?.userId ||
    user.name === order?.user ||
    user.nick === order?.user ||
    user.nick === order?.userNick
);

addOrder({
  product: product.name,
  productId: product.id,
  quantity: 1,
  price: Number(product.price),
});

const updatedProduct = updateProductStock(product.id, 1);
setProducts(loadProducts());
```

### 해결 후 달라진 점

- 주문 후 재고가 바로 줄어들어 흐름이 자연스러워졌습니다.
- 마이페이지와 주문 데이터 연결도 덜 어색해졌습니다.

### 이번 경험으로 배운 점

- 포트폴리오 프로젝트라도 "기록만 저장"하면 데모처럼 보입니다.
- 사용자가 버튼을 눌렀을 때 눈에 보이는 변화가 있어야 완성도가 올라갑니다.

### 면접에서 이렇게 설명하면 좋음

"처음에는 주문 저장만 되면 된다고 생각했는데, 실제로는 재고가 함께 줄어야 사용자 입장에서 더 자연스럽다고 판단했습니다. 그래서 주문 저장과 상품 상태 반영을 같이 연결했습니다."

## 4. 테스트 환경 복구 과정

### 문제 상황

- 누구: 포트폴리오 제출 전 품질 점검을 하던 개발자
- 언제: `npm test` 실행 단계
- 어디서: 기본 테스트 파일
- 무엇을: 기본 테스트가 프로젝트 실제 구조와 맞지 않아 실패
- 왜 중요했는가: 테스트가 깨진 상태는 프로젝트가 덜 마감된 인상을 줌
- 어떻게 확인했는가: `npm test -- --watchAll=false` 실행 후 실패 로그 확인

### 왜 문제가 생겼는지

- 기본 CRA 예제 테스트가 프로젝트 실제 구조와 맞지 않았습니다.
- 라우터 환경과도 충돌이 있어 단순 화면 렌더 테스트가 계속 실패했습니다.

### 처음에 했던 잘못된 접근

- 기본 테스트를 조금만 바꾸면 될 거라고 생각했습니다.
- 하지만 현재 테스트 환경에서는 라우터를 직접 가져오는 방식이 더 불안정했습니다.

### 해결 방법

- 라우터에 의존하는 화면 테스트 대신, 현재 프로젝트에서 핵심이 되는 저장 로직을 검증하는 테스트로 바꿨습니다.
- 사용자 저장/조회, 상품 재고 차감 로직을 테스트해 "기본 품질 검증이 가능하다"는 상태를 만들었습니다.

### 수정 전 코드

```js
import App from "./App";

test("renders learn react link", () => {
  render(<App />);
  const linkElement = screen.getByText(/learn react/i);
  expect(linkElement).toBeInTheDocument();
});
```

### 수정 후 코드

```js
beforeEach(() => {
  localStorage.clear();
});

test("현재 사용자 저장과 조회가 동작한다", () => {
  const user = { user_id: "tester", nick: "테스터", admin: 0 };

  setCurrentUser(user);
  expect(getCurrentUser()).toEqual(user);

  clearCurrentUser();
  expect(getCurrentUser()).toBeNull();
});

test("상품 재고를 차감하면 재고와 상태가 함께 갱신된다", () => {
  const [firstProduct] = loadProducts();
  const originalStock = Number(firstProduct.stock);
  const updatedProduct = updateProductStock(firstProduct.id, 1);

  expect(updatedProduct.stock).toBe(Math.max(0, originalStock - 1));
});
```

### 해결 후 달라진 점

- 테스트가 통과하는 상태로 정리됐습니다.
- 포트폴리오에서 "기본 품질 확인을 해봤다"는 근거가 생겼습니다.

### 이번 경험으로 배운 점

- 테스트는 많아야 좋은 것이 아니라, 현재 프로젝트 구조와 맞아야 의미가 있습니다.
- 첫 프로젝트에서는 작은 테스트라도 통과하는 상태를 만드는 것이 중요합니다.

### 면접에서 이렇게 설명하면 좋음

"기본 예제 테스트가 실제 프로젝트와 맞지 않아 오히려 잡음이 됐습니다. 그래서 현재 구조에 맞는 최소 테스트로 바꾸고, 저장 로직과 재고 반영처럼 실제 흐름에 중요한 부분을 검증하도록 바꿨습니다."
